ODbL distinctions matter: under [ODbL §§4.2–4.6](https://opendatacommons.org/licenses/odbl/1-0/), public conveyance notices, public use of a Produced Work and public use of a Derivative Database have distinct conditions. Section 4.6 includes an offer of machine-readable derivative data or the alterations/method in its applicable circumstances; it is not resolved by attribution alone. Whether the exact PERIX database, API responses and combination with other data trigger those provisions needs qualified review. Do not presume that ODbL and realtime ShareAlike automatically do or do not combine compatibly. CC deeds are summaries, not substitutes for the legal codes. Attribution and any disclaimer should preserve supplied notices and avoid claiming provider endorsement.

## 4. Staging gates and sequence

1. **Isolation first.** An authorized operator must confirm target project/environment/service/deployment and actual backend DB destination and database name against production without exposing secrets. Confirm network egress, provider and billing settings, background-worker topology and auto-activation state. Provision or identify a genuinely disposable isolated database, not just a similarly named service. Preserve existing staging and production data; never point the legacy destructive test fixture at either. Do not deploy the dirty checkout.
2. **Rollback before writes.** Inventory the active network, graph, restrictions, overlays and atomic generations and obtain an approved tested backup/restore or independent immutable replacement strategy. `mobility/osm_store.py` replaces active graph metadata and then deletes graph documents whose `graph_v` differs from the new version. Therefore an import can destroy prior snapshot documents in the target database; old-network rollback cannot be assumed to reconstruct the old graph. Multiple overlapping importers also need exclusion and failure-path tests. Do not run imports or enable automatic jobs until isolation, retention and rollback are proved.
3. **Build identity.** Select an explicitly reviewed change set without unrelated WIP; produce an isolated package and manifest with file hashes, frontend/backend pairing and nonsecret configuration. Verify exact deployed runtime and frontend hashes after any separately authorized staging deployment. Re-check source licensing, provenance and network/date alignment, then use an appropriately dated, coverage-audited snapshot. Never treat a successful build or an HTTP 200 as a full staging pass.

**Staging package rule (2 Nov, local, no commit/deploy):** the working tree is dirty by design (unrelated WIP present), so nothing may be deployed as-is. The reviewed change set for any future staging package is *only* the task hunks listed in `perix-hunk-classification-20261102.json` (94 analyzed hunks: 59 heuristic OURS across schedule-only legs, version-bound static identity with notices/publisher, `feed_info` parsing, notice identity, V2 manifest, schedule credit and their tests/docs). Per-file working-tree SHA-256 hashes are in `perix-staging-package-hunks-20261102.json` for later deployed-runtime comparison. Heuristic misses positively attributed by author review and also INCLUDED: the `import os/tempfile` + Env-doc lines for the tempfile isolation, the `mock_open` cleanup deletions in `test_daily_network_recovery.py`/`test_mobility_civil_day.py`, and the `assert not Path(...).exists()` tempfile assertion. Everything else (motion continuation/expiry logic, `BusinessMap.*`, `useCityDiscovery.ts`, `gateway.ts`, motion/preview API extensions, fleet/marker wiring beyond the credit block) is EXCLUDED pending separate review, even where it overlaps the same files. The responsible reviewer confirms hunk-by-hunk, builds the clean package, and only then may staging proceed.
4. **Functional and freshness checks.** Against the isolated target, test actual verified restrictions/overlays, generation identity, service-date rollover, repeated stops, no-trip-timestamp continuation, stale and out-of-order forecast handling, preview binding, attribution and correct GPS/forecast/model labelling. Capture failing and passing cases for N8, tram 6, N5, bus 52 and representative other lines. Inspect desktop and mobile rendering without changing `/home` or `/locator` design. Do not label mapped signals or speed tags as observed traffic.
5. **Resilience and capacity.** Test full app restart and independently controlled multiple processes, concurrent imports/activation and polling, failure during graph creation/activation, and tested restoration of the previous version. Use the preapproved workload and metrics below: actual concurrent clients and poll intervals, request/error rates, p50/p95/p99 latency, CPU/memory, DB resource consumption and provider call counts. Do not extrapolate local MongoDB timing to hosted capacity.

**Capacity plan (proposed limits, operator approves before running; staging only, never production):** workload = graduated concurrent readers (proposed steps 10 → 50 → 150 clients) replaying the real cadence — `GET /mobility/v2/vehicles` every 8 s, `GET /mobility/v2/map` every 300 s, plus `stops`/`arrivals` reads at 30 s — against the isolated staging deployment with workers in their intended state. Record per-endpoint request/error rates and p50/p95/p99 latency, app CPU/memory, MongoDB primary CPU and slow-query count, and realtime-feed fetch count (must not multiply per client). Proposed gates: zero 5xx, error rate < 1%, p95 vehicles < 800 ms, p95 map < 2 s, p99 map < 5 s, MongoDB primary CPU < 70%, no OOM/restart. Stop conditions: any gate breached for two consecutive steps, any failed import/activation, or any backup/restore anomaly — stop, record, do not proceed to a higher step. Separately: one controlled restart of the staging backend (verify generation identity and schedule-only behavior return unchanged), one concurrent import-versus-activation race (the second actor must lose cleanly with a BUSY/state error, never a half-published network), and one restore of the previous network+graph from the approved backup with runtime hash re-verification. All results, hashes and discrepancies go into the sign-off record.
6. **Sign-off.** Record runtime versions, hashes, dated inputs, source notices, results and unresolved discrepancies. Responsible technical and licensing reviewers must explicitly approve their respective gates. Production deployment remains a separate decision and requires separate user approval.

**Local startup control:** `MOBILITY_WORKERS_ENABLED=false` now prevents the local code from starting the four in-process Mobility workers or requesting startup precompute. Default `true` preserves existing startup; invalid values fail startup. This local option is not set or deployed anywhere. It does not disable unrelated startup migrations, schedulers or other services; it is not proof of isolation. In particular, `MOBILITY_SYNC_AUTO_ACTIVATE=false` alone does not stop OSM snapshot imports.

**Disposable rollback experiment:** in a newly created PID/path-verified loopback MongoDB 7.0.45 database, a synthetic graph was copied into memory, a second snapshot was imported, and the original graph's ways and signals were confirmed deleted. With all test readers/writers quiesced, a sequential region-scoped restore recovered the exact original documents and active metadata, without touching a synthetic other-region sentinel. After a graceful restart of that disposable database, the supervisor verified the restored graph's active version, way IDs and signal ID. The run passed 16 tests; its report is `perix-mongo-isolated-20261102\synthetic-graph-rollback-v2-restart\report.json`. The test copy was in memory only, and restoration was not atomic. This is **not** a production backup utility, a full application restart, an online rollback, a test of real data/indexes/overlays, or validation of a hosted MongoDB version. It does not clear the staging isolation or rollback gate.
